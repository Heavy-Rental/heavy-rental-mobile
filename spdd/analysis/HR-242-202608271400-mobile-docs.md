# Analysis: HR-242 mobile documentation alignment

## Problem

The Android repo practiced informal SDD under `specification/` while sibling Heavy Rental repos adopted OpenSpec `spec-driven-with-adr`, OpenSPDD, and MADR. Root README/CHANGELOG were still the Best-README-Template. Several product/API statements contradicted Spring OpenSpec and this app's code:

| Stale claim | As-built |
|-------------|----------|
| First-time Google → `ROLE_USER` | Spring FR-AUTH-L-001b → `ROLE_DRIVER` |
| `ROLE_DRIVER` locked out of all business routes | Driver may call bookings/deliveries/returns |
| Booking APIs only on backend branch `HR-80` | Present on Spring `develop` |
| Domain still "one asset only" | Client `items: List<AssetLine>`; Spring FR-BDR-007 |
| Default mock URL in `mocks/README.md` | Default is Spring `:8080` |

CI/Release YAML already exists (HR-157/218/233) with no OpenSpec capability describing it. `android-ci.yml` is a leftover.

## Goals

- Same three-layer stack as the portal and devcontainer repos.
- Accurate product SDD vs code and Spring OpenSpec.
- Index CI callers without claiming portal CD.

## Non-goals

- Changing Kotlin runtime behaviour.
- Deleting `android-ci.yml` or `BLANK_README.md` in this change.
- Rewriting every Gherkin file into OpenSpec deltas.

## Risks

- Duplicate sources (`specification/` vs `openspec/`) — mitigated by conflict rule and product-features index.
- Restoring stale backend facts from git history — mitigated by ADR-0006/0008 and AGENTS.md warnings.
