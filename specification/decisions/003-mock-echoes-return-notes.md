# ADR 003: Mockoon echoes returnNotes on the return-status route

## Status

Accepted (v1)

## Context

`HR-100` added an operator-entered `returnNotes` field to the return-status update flow:
`PATCH /api/returns/{bookingId}/status` now takes a `ReturnStatusUpdateRequest` body
(`bookingStatus` + `returnNotes`, see [ADR 001](001-openapi-as-api-source.md) and
[heavyrental-openapi.yaml](../api/heavyrental-openapi.yaml)). The Kotlin client, OpenAPI contract,
and product/domain specs were all updated for this, but the Mockoon mock (see
[ADR 002](002-mock-strategy.md)) was not: every Mockoon route, including this one, serves a
**static** `FILE` fixture regardless of the request body. Testing a return completion against
Mockoon always showed a canned `returnNotes` value (usually `""`), never the note an operator
actually typed — making the mock unable to demonstrate or manually verify the one thing HR-100
added.

## Decision

1. `mocks/.generated/return-item.json` (the fixture Mockoon serves for
   `PATCH /api/returns/{bookingId}/status`) uses Mockoon's `{{body 'path' 'default'}}` templating
   helper for exactly two fields:
   ```json
   "returnNotes": "{{body 'returnNotes' ''}}",
   "bookingStatus": "{{body 'bookingStatus' 'COMPLETED'}}"
   ```
   so the response echoes back whatever was actually sent in the PATCH body (falling back to an
   empty note / `COMPLETED` status if the field is omitted, e.g. from a manual curl without one).
2. This is generated by `scripts/prepare-mocks.mjs`, not hand-edited (ADR 002 rule 5 still
   applies to the generated file itself) — the templating strings are written into a
   Mockoon-only fixture object, kept separate from the plain, realistic value used for the
   OpenAPI bundled example that Prism and documentation consume (that templating syntax means
   nothing to Prism or a human reading the spec).
3. Scope is deliberately narrow: only the return-status route gets this treatment. Every other
   Mockoon route — including the sibling `PATCH /api/deliveries/{bookingId}/status` — keeps the
   plain static-fixture behaviour from ADR 002. Deliveries has no notes field to echo, and there's
   no product need yet to make other routes reflect their request bodies.

## Consequences

**Positive**

- Manually completing a return against Mockoon (Postman or the app) shows back the note that was
  actually typed, instead of a canned value — the mock now demonstrates the feature HR-100 added.
- `npm run mock:verify` can assert the echo, catching regressions if the fixture generation logic
  changes.

**Negative / trade-offs**

- Mockoon still does not validate the request body — a PATCH with no `returnNotes` at all still
  returns `200` with `returnNotes: ""` rather than the `400` the OpenAPI spec documents for
  "Invalid transition or body". Real validation still requires the Spring Boot backend.
- Prism (the other mock option in ADR 002) does not get this echo behaviour — it still serves the
  static OpenAPI example. Anyone testing the note round-trip specifically must use Mockoon.
- One more small, mock-tool-specific detail to keep in mind when reading `mocks/.generated/return-item.json` —
  it is the one generated fixture that is not literally "the example data," despite ADR 002 rule 5
  still governing how it's produced.

## Alternatives considered

| Option | Why not (for now) |
|--------|---------------------------|
| Leave it static, document as a known gap | Simpler, but leaves the mock unable to actually demonstrate HR-100's note round-trip during manual QA |
| Add Mockoon rules + a second (400) response for missing `returnNotes` | More realistic, but real request validation is already covered by the Spring Boot backend target; not worth the added Mockoon config complexity for v1 |
| Give every PATCH route this echo treatment (including deliveries) | No field to echo for deliveries yet; broader change than the current need |
